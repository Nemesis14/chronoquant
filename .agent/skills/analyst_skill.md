# Analyst Skill

Execution guide for producing Quarto-renderable analysis notebooks.
Single source of truth for notebook structure, code conventions, finding patterns, and workflow.

---

## Notebook Structure

The notebook begins with a **Raw cell** containing Quarto YAML frontmatter — not a markdown
heading. Required sections follow in order:

```markdown
## Objective
## Setup
## <Check 1>
## <Check N>
## Summary
```

**Objective** — always first after the frontmatter. Written as prose. States what is being
analyzed, which table/model/dataset, asset, granularity, and spec reference. Must not open
with a table or code cell — prose comes first.

**Summary** — always last. Written after all checks have run. Contains real
computed findings — no placeholders.

No separate `Conclusion` / `Conclusions` section. Conclusions belong inside each check.

### Document Frontmatter (Raw cell)

The **first cell** of every notebook must be a Raw cell (cell type = `"raw"`) containing:

```yaml
---
title: "<Human-readable title, e.g. OHLCV Table — Data Quality and Completeness Audit>"
subtitle: "<Spec ID and context, e.g. Analysis 0024 | solusdt 1m>"
date: "<YYYY-MM-DD>"
---
```

Do **not** use a markdown `# Heading` as the document title. Quarto renders the frontmatter
`title` and `subtitle` as a styled header automatically. A redundant `#` heading creates a
duplicate visible title in the rendered HTML.

### Objective block example

```markdown
## Objective

This notebook audits the quality of the `ohlcv` table for SOLUSDT 1-minute
candles. It checks for time-range completeness, gap density, duplicate timestamps,
and null patterns in key price/volume columns.

**Table:** `ohlcv` | **Asset:** SOLUSDT | **Granularity:** 1-minute candles
**Date:** 2026-06-16 | **Spec:** `_doc_/analysis/0024_ohlcv_table_spec.md`
```

## Check Cell Pattern

Every methodological check follows this three-cell sequence:

1. **Markdown definition cell** — purpose, method, interpretation, action rule.
2. **Code cell** — runs the check; renders a labelled table or figure.
3. **Finding** — generated by code or written as markdown; immediately after the result.

Markdown template:

```markdown
### <Check title>

**Purpose.** This table/figure checks <what is being checked>.

**Method.** Uses <source tables/files/columns> and computes <metric> at <grain>.

**Interpretation.** Healthy: <condition>. Suspicious/failing: <condition>.

**Action rule.** If the check fails, <next action>.
```

Each field must be its own paragraph (separated by a blank line) so that Quarto
renders them on distinct lines. Writing them as a continuous block collapses them
into a single line in the HTML output.

Finding pattern (computed):

```python
from IPython.display import Markdown, display

failed = int((fold_gaps["gap_bars"] < 60).sum())
if failed == 0:
    display(Markdown("**Finding:** ✅ All folds satisfy the 60-bar embargo rule."))
else:
    display(Markdown(f"**Finding:** ⚠️ {failed} folds violate the 60-bar embargo rule."))
```

Finding pattern (written markdown):

```markdown
**Finding:** ✅ No leakage detected. All feature availability timestamps are ≤ `open_time`.
```

Findings must derive from computed tables, metrics objects, or scalar values —
never from visual inspection of plot images.

## Code Style

- **Data access:** DuckDB-first — SQL for filtering, joining, aggregation, window functions, sampling, large scans.
- **Large transforms:** Polars when in-memory logic is complex to express clearly in SQL.
- **Display/plotting inputs:** pandas only for small final display frames.
- **Charting:** seaborn (primary); matplotlib as fallback/customization layer (axis formatters, reference lines). Plotly forbidden unless spec explicitly requests interactive HTML.
- Use `duckdb.connect(db_path, read_only=True)` — never write to the DB.
- Every chart cell must call `plt.show()`.
- No bare `print()` — use displayed tables, generated Markdown, or `logger.*`.
- No manual numbering in headings, captions, or labels. Let Quarto handle it.

### Displayed table rules (mandatory)

Every report table cell **must** end with `display_analysis_table(df)`.

**Never** use:
- a bare dataframe variable as the last expression (`summary_df`, `gaps_df`, etc.)
- `display(df)` or `display(df.head())` directly on a raw DataFrame
- `df.style` directly without going through `format_analysis_table`
- `df.head()` as the final cell expression

**Always:**
- call `display_analysis_table(df)` as the last statement in every table cell
- import at top of Setup cell: `from table_formatting import format_analysis_table, display_analysis_table`
- add the src path before importing: `sys.path.insert(0, "src")`

`display_analysis_table` hides the pandas index and enforces all numeric formatting rules
(see `analysis_presentation_skill.md` — Numeric Formatting section).

### Return and Volatility Distribution

When visualizing the distribution of returns or realized volatility (log returns,
per-period volatility), always use **box plots** — not histograms or KDE plots.
Box plots simultaneously show median, IQR, whiskers, and outliers, and scale well
for period comparison (one box per year / half-year). Use `seaborn.boxplot` with
the time period on the x-axis.

## Analysis Helper Modules

Reusable analysis logic belongs under `_doc_/analysis/src/`, not duplicated across notebooks.

- Create a helper when the same logic would appear in two or more notebooks.
- All public functions must have type annotations and Google-style docstrings (see `coding_skill.md`).
- Helpers must not write to DuckDB, mutate production tables, or change model artifacts.

Import in the Setup cell:

```python
import sys
sys.path.insert(0, "_doc_/analysis/src")
from embargo_checks import compute_fold_gaps
```

## Forbidden Placeholder Text

Never write:

- `futtatás után kitöltendő`
- `to be filled after running`
- `TODO after execution`
- `interpret after running`
- any blank interpretation or finding section

If a finding depends on execution, generate it in code:

```python
display(Markdown(f"**Finding:** ⚠️ {violations:,} rows have `available_ts > open_time`."))
```

## Run-and-Fill Workflow

1. Write all markdown definition cells and executable code cells.
2. Ensure every finding is generated programmatically — no placeholder text.
3. Execute all cells from a clean kernel.
4. Write the Summary from computed results.
5. Render: `quarto render _doc_/analysis/<slug>.ipynb --execute`
6. Verify no forbidden placeholder text remains in the rendered output.
7. Verify all result-producing cells have `#| label:` and caption tags (see `quarto_analysis_defaults.md`).

---

## Flagging Issues

If a critical issue is found (leakage, broken CV, wrong null count):

1. Document it in the check's local finding.
2. Add it to the Summary.
3. Append to the triggering Jira/spec notes:

```markdown
[analyst] Critical finding — <YYYY-MM-DD>
Issue: <one-line description>
Notebook: _doc_/analysis/<slug>.ipynb
Rendered: _doc_/<slug>.html
```

4. Create a `todo_` ticket for the responsible agent.
